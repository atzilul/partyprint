## המטרה
להגדיל פניות מתאימות להזמנת חולצות בעיצוב אישי, באמצעות גילוי במנועי חיפוש ובתשובות עם חיפוש ב-AI.
השרשרת היא סריקה → הבנת העמוד ובחירת canonical → אינדוקס → הופעות רלוונטיות → ביקור → פנייה שנשמרה → טיפול עסקי.
אין ערבוב בין השלבים: HTTP 200 אינו אינדוקס, קליק אינו פנייה ופנייה אינה רכישה ששולמה.
אין יעד ״מקום ראשון ב-ChatGPT״. מודדים חשיפה וציטוטים במדגם מוגדר, פניות בפועל ודיוק מידע.

## מצב היסטורי במועד הכנת התכנית
- המקור הנבחר הוא main ב-GitHub atzilul/partyprint; האתר החי הוא partyprint.co.il על Hostinger.
- PR #3 עדיין פתוח. מסמכי המחקר הקודמים בענף; תיקוני היישום לא פורסמו.
- קוד היישום הנבדק ב-b99bf17 עבר חמש בדיקות כלי, בניית production ו-109 בדיקות מקומיות בסשן הקודם. אין זו ראיה לפריסה או לאינדוקס.
- בדיקת HTTP קודמת מאותו יום מצאה 59 עמודי HTML קיימים עם 200; נמצאו סימון דף בית משוכפל ו-soft 404. הנתון היסטורי, לא בדיקה מחדש בכל קריאת המסמך.
- Windsor מותקן, אך פעולות הקריאה שלו אינן זמינות גם בסשן זה. נתוני GSC/GA4 ומצב האינדוקס בחשבונות לא נשלפו.
- מצב פריסת Hostinger אינו מאומת. אין מסנכרנים את עותק Sites לפני אימות production.
- 106 הביטויים ו-90 השאלות הם רשימת מועמדים מהמחקר, ולא תחליף לנתוני ביקוש או המרה.

## מה ראשון ומה מחכה
P0 הוא תנאי בסיס לתכנית: גישה נכונה, עובדות, שחרור תקין, תקינות פנייה ויכולת אבחון. הוא אינו טענה שכל פריט הוא גורם דירוג.
P1 הוא תוכן/טיפול בעל התאמה ישירה לחבילות ולקושי להזמין.
P2 הוא הרחבה שתיבחן לפי ביקוש ומידע. P3 נשמר לביטויים רחבים בהתאמה נמוכה יותר עד שיהיו ראיות.

סדר העמודים הראשוני:
1. P16 רווקים; P17 רווקות; P03 משפחה.
2. P04 צוות ועסק; P01 הדפסה; P02 עיצוב מתמונה/רעיון.
3. P15 תכנון צוות; P05 אירועים; P07 מתנה אישית; P12/P13 ילדים; P18 יום הולדת.
4. שאר עמודי ההשראה לפי D07, כולל מתנות לעובדים, הורים וקהלים משניים.

לכל פריט בקובץ המשימות יש מצב נוכחי. ״מוכן ב-PR״ אינו ״פורסם״; ״הוכן בתכנית״ אינו ״בוצע באתר״; ״ממתין לתלות״ אינו שגיאת חיבור חדשה.
אין ליצור עמוד נפרד לכל וריאציית יחיד/רבים, גיל, עיר או שגיאת כתיב. אין לייצר 196 עמודים מ-196 רשומות המחקר.

## שני מסלולים שאפשר לקדם במקביל
מסלול נתונים: R02 מפעיל חשבון → D02 נכסים → D03/D04 נתונים → D06 איכות → D07 סדר עדיפות → M01 דוח עסקי. D01 מספק את מסלול הקריאה דרך Windsor; כשפעולותיו אינן זמינות, מפעיל חשבון יכול להכין ייצוא מורשה מהנכס המאומת לפי אותו מפרט. מקור חלופי מתועד ואינו מחייב חיבור מחדש.
מסלול שחרור: R04 אישור הגרסה + T01 התאמת בדיקות → V01 מיזוג → V02 קבלת Hostinger → T02 בדיקה חיה → V03/V04 הודעה למנועים → V05 מעקב קליטה.
מסלול תוכן יכול להתחיל מטיוטות עם עובדות קיימות: R03 עובדות + C00 בריפים → ששת עמודי הליבה → הרחבת קישורים → מקרי לקוח והעמודים הבאים.
אם נתוני Windsor מתעכבים, מכינים תוכן ותשתית לפי התאמה ראשונית ומתעדים שהעדיפות טרם מבוססת על נתונים. אין ממלאים נפח חיפוש או מספר פניות בניחוש.

## מפת עמודים ותפקידי תוכן
- חולצות למסיבת רווקות/רווקים: עמודים מסחריים; עמודי המתנות מספקים רעיונות ומפנים אליהם.

- עיצוב אישי: תהליך יצירתי; הדפסה על חולצות: בחירת שירות והבנת מחיר.
זו השערת ארכיטקטורה עד C24. נתוני query+page וערך התוכן קודמים לכל איחוד ו-301.

## כללי Google ו-AI שעליהם התכנית נשענת
הגישה היא תוכן מועיל, תשתית קריאה, זהות עסקית ודיוק. Google אינו דורש llms.txt או schema ייחודי כדי להופיע בתשובות AI.
OAI-SearchBot מיועד לחיפוש ו-GPTBot לאימון; ב-Claude הגישה של SearchBot/Claude-User נפרדת מתפקיד ClaudeBot באימון.
פתיחת גישה אינה מבטיחה אזכור. אין צורך להרחיב הרשאות אימון כתנאי קידום, ואין לשנות העדפות אימון בלי החלטה מתאימה.
הנתיבים הפרטיים נשארים מוגנים, ונתוני הלקוחות אינם חומר לקידום.
הבדיקה החודשית מפרידה בין אזכור, קישור, עמוד מתאים ודיוק מידע. התנהגות מודל ללא חיפוש אינה מדד לקליטת פריסה.

## איך סוגרים משימה
ראיה מתאימה + תאריך + בודק + מצב בפועל. לדוגמה:
- עמוד: קישור לגרסה, מקור לעובדות, תוצאות QA וקבלת פריסה.
- נתונים: מקור, נכס, פילוחים, תאריכים, זמן שליפה ומגבלות כיסוי.
- אינדוקס: סטטוס בכלי המנוע ותאריך בדיקה; אין המצאה על סמך 200.
- AI: נוסח השאלה, הכלי, מצב חיפוש וראיה לתוצאה; כיסוי המדגם מצוין.
- קבלת API: ״הודעה התקבלה״; לא ״העמוד דורג״.
